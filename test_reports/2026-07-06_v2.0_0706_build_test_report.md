## 2. 測試範圍與方法

測試目標：確認「Table 85 / Table 22 / Table 15 / Table 117 NFCEE Status 由 if/else 改為查表字典」這次重構在打包後的行為，與重構前一致（除了三個已與使用者確認過的預期輸出變更）。

**方法與環境限制**：
- 用 `python Decoder.py`（原始碼、正確設定 `PYTHONIOENCODING=utf-8`）跑過完整互動選單流程（選單 → mode 2 → 輸入 raw hex → 解碼輸出 → 離開），確認端到端流程正常。
- 對打包後的 `.exe`，嘗試用相同方式（管道輸入）驅動互動選單，但受限於一個**既有、與本次修改無關**的問題：`Decoder.py` 選單裝飾用字元在 stdout 非真正互動式主控台（如管道）時會用 `cp950` 編碼輸出，遇到框線字元/顏文字會丟出 `UnicodeEncodeError`；且 `PYTHONIOENCODING` 環境變數對打包後的 exe 無效（PyInstaller bootloader 未套用）。已用未修改過的原始碼重現同樣錯誤，證實這是舊有問題（詳見專案記憶 `project_console_app_cp950_encoding_issue`），不是本次或本次打包造成的迴歸。
- 因此本次對 `.exe` 的驗證改採：(a) 確認 PyInstaller 打包記錄顯示所有異動模組都被正確分析、無 import 錯誤；(b) 直接對打包進 exe 的**相同原始碼**（PyInstaller 不會轉換程式邏輯，只是封裝）用函式呼叫方式逐一驗證 4 個異動函式在 `vendor=None`（forum 2.0）與 `vendor=Nxp` 兩條路徑下的輸出，等同於驗證了封裝進 exe 的實際邏輯。

## 4. 發現的既有問題（非本次修改造成）

- **主控台選單編碼問題**：`Decoder.py` 的 `print_menu()` 在 stdout 未接到真正互動式主控台時（例如自動化測試用管道輸入），因裝飾用字元（框線、顏文字含泰文 Unicode）用 `cp950` 編碼會丟出 `UnicodeEncodeError`。已用未修改的原始碼重現同樣錯誤，確認是舊有問題。詳見專案記憶 `project_console_app_cp950_encoding_issue`。這個問題**不影響**一般使用者直接雙擊執行 exe 或在真正的終端機視窗（cmd/PowerShell/Windows Terminal）裡執行的情況，只影響自動化管道測試。是否要修復，待使用者決定。

## 5. 結論

打包成功，檔名符合需求（`NCI_Decoder_v2.0_0706.exe`）。本次重構的 4 個查表字典改動在 forum 2.0、Nxp、（死代碼的）2.3 三條路徑上皆驗證通過，行為與預期（含 3 項已確認的刻意輸出變更）完全相符，未發現迴歸。建議使用者在真正的終端機視窗手動執行一次 exe 做最終視覺確認（尤其是選單畫面本身，因為管道測試環境的既有編碼限制，這部分無法在本次自動化測試中直接驗證）。
