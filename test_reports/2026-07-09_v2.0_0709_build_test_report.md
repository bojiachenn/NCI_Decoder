## 2. 測試範圍與方法

因本次打包**未修改任何解碼邏輯**，測試重點是確認「重新打包後的行為與 0707 版一致」（迴歸測試），而非驗證新功能。

**方法與環境限制**（既有限制，詳見專案記憶 `project_console_app_cp950_encoding_issue`）：打包後的 `.exe` 在 stdout 非真正互動式主控台時會因選單橫幅的 `cp950` 編碼問題無法用管道驅動，因此本次驗證採用：
- (a) 對封裝進 exe 的**相同原始碼**，用 `PYTHONIOENCODING=utf-8` 直接執行 `python Decoder.py`，以管道輸入驅動互動選單，測試 mode 1（讀檔）與 mode 2（單筆 raw hex）；
- (b) 直接啟動打包後的 `dist/NCI_Decoder_v2.0_0709.exe`（雙進程各啟動一次），確認能在真正的 Windows Console 下正常啟動、不崩潰，再以 `taskkill` 結束測試行程（未逐字元比對選單畫面，僅確認程序存活、無立即崩潰）。

## 3. 測試案例與結果

測試資料：`NCI_ref/raw_log.txt`，同時包含 NXP（`NxpNciX`/`NxpNciR` 標籤）與 ST ST54L（`StNfcHal`，含 `(#0000N)` 分段、大小寫 Tx/tx 續行、`(hidden)` 遮蔽封包）兩種格式混合的樣本，是測試 log-profile 機制是否正確依 `vendor` 選字挑選 profile、且忽略不屬於自己格式的行的良好案例。

|---|---|---|
| Mode 1，`vendor=Nxp` | 讀取混合檔，僅應解出 NXP 標籤的 4 個封包（`CORE_RESET_CMD/RSP/NTF`、`CORE_INIT_CMD/RSP`），ST 行應原樣通過（filter=remain_all） | ✅ PASS — 4 個封包正確解碼，欄位（Reset Type、NCI Version、NFCC Features 逐位解析等）內容正確；5 筆 ST 行未被誤判，原樣輸出 |
| Mode 1，`vendor=St` | 同一檔案，僅應解出 ST 標籤的封包，NXP 行原樣通過 | ✅ PASS — 5 個序號（#00001~#00007，含 #00004 續行合併）全數處理：3 個一般封包解碼正確（`CORE_RESET_CMD/RSP/NTF`、`CORE_INIT_CMD/RSP`）、2 個 `(hidden)` 封包正確標示 `[REDACTED: packet #0000N payload hidden by HAL]`；跨行分段封包 `#00004`（`Rx 60 00 1F...` + `rx 20 01` 續行）正確串接為 34 bytes 並解出 `CORE_RESET_NTF`，與宣告長度 `3+0x1F=34` 一致；5 筆 NXP 行未被誤判，原樣輸出 |
